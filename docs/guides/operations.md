# 操作指南

这份指南从配置第一位队员开始，介绍 Runtime、权限、Camp、工程讨论场景、Skill、MCP、运行监控和团队记忆的基本使用方式。

安装与首次启动见：[安装指南](installation.md)。

## 1. 配置队员

队员身份和 Agent Runtime 是两个不同的层次。

名字、形象、职责、性格与共同经历决定这名队员是谁；Runtime、模型和权限决定他通过什么能力参与任务。

### 用 Member Studio 招募

可以先在 Camp 中描述想招募的伙伴，例如：

```text
我想招募一位擅长拆解复杂问题、说话直接、会主动指出风险的长期队员。
请帮我整理他的名字、角色、职责、性格、工作准则和适合的 Runtime。
```

Member Studio 会把描述整理成可确认的队员方案。只有 Principal 确认后，新队员才会正式创建。

### 在队员工作区完善配置

建议至少检查这些内容：

- **名字与形象**：让队员在长期会话中容易辨认；
- **团队角色**：说明他在队伍中主要负责什么；
- **专业职责**：写清楚应主动处理的工作；
- **协作边界**：说明哪些事需要先询问、交给别人或等待确认；
- **性格与表达方式**：保留差异，但不要用冗长设定占用任务上下文；
- **Runtime 与模型**：选择已经显示为可用的安装；
- **权限与运行参数**：根据工作区风险和任务类型选择。

第一次组队时，建议从两到四名队员开始。角色分工比人数更重要，例如探索、质疑、推进和记录。

## 2. 选择 Runtime 与模型

在队员的「运行配置」中选择：

1. Agent Runtime；
2. Runtime 安装；
3. 模型或 Runtime Default；
4. 推理强度等可用参数；
5. 权限模式与沙箱设置。

`Runtime Default` 不依赖模型目录，可以直接使用。显式模型需要 Runtime 已完成可用性检查，并返回当前模型目录。

切换 Runtime 不会自动把旧 Runtime 的模型和权限语义套到新 Runtime 上。保存前应重新检查当前字段。

## 3. 权限怎么设置

如果是在**你自己的、可信并且可以恢复的项目目录**中工作，希望队员尽量少被权限弹窗打断，可以使用最高权限模式。

最高权限通常允许 Runtime 修改文件、运行命令，并减少逐次确认。启用前建议确保项目已有 Git 提交或其他可用备份。

对于陌生仓库、下载的第三方代码、包含敏感文件的目录，先使用默认、询问或计划模式，不要直接开启最高权限。

### 各 Runtime 的高权限配置

| Agent Runtime | 高权限配置 |
|---|---|
| Claude Code | `permission_mode = bypassPermissions` |
| Codex CLI | `sandbox_mode = danger-full-access`；`approval_policy = never` |
| OpenCode | `permission = allow` |
| GitHub Copilot CLI | `allow_all = on` |
| Antigravity | `mode = accept-edits`；`sandbox = off`；`dangerously_skip_permissions = on` |
| Kiro CLI | `trust_all_tools = on` |
| Qoder CLI | `permission_mode = bypass_permissions` |
| CodeBuddy | `permission_mode = bypassPermissions` |
| Qwen Code | `approval_mode = yolo` |
| TRAE CLI CN | `permission_mode = bypass_permissions` |

权限决定 Runtime 原生工具可以做什么。Rovai 的审批、运行记录和可观察性不能代替操作系统权限、Runtime 沙箱或项目备份。

## 4. 创建 Camp

Camp 围绕一个真实项目、任务或长期目标建立。

创建时重点确认：

- **名称与目标**：用一句话说明这支队伍要解决什么；
- **项目目录**：选择队员实际工作的目录；
- **队员**：只加入与当前目标有关的伙伴；
- **Lead**：选择默认负责接住任务和整理结果的队员；
- **协作方式**：决定是直接对话、双人追问，还是集体讨论。

项目目录可以是普通文件夹、空 Git 仓库或已经存在提交的 Git 仓库。Git 能力会按目录实际状态动态启用，不是创建 Camp 的必要条件。

## 5. 在 Camp 中分配工作

### 直接发送

不指定队员时，由当前 Camp 的默认 Lead 接住任务。

### @ 指定队员

需要特定角色处理时，直接在消息中 @ 对应队员。例如：

```text
@叮叮 先调查现有实现和相关文档，整理三个可行方向。
@芝士 检查这三个方向里最容易被忽略的风险。
```

### 使用附件

可以把文档、图片或其他任务材料加入 Camp。队员会在当前 Camp 的受控附件视图中读取这些内容。

不要把密码、Token、私钥或其他凭据作为普通附件发送。

## 6. 选择合适的协作方式

### 普通会话

适合目标明确、由一名队员主导推进的任务。

### `grill-duo`

适合方向模糊、需要补齐约束或需要独立反证的决策。

一名队员负责持续追问，另一名队员从不同角度检查事实和风险。最终决定仍由 Principal 作出。

### `campfire`

适合需要整支队伍参与、没有唯一答案的问题。

队员先分别给出观点，再整理共识、分歧、证据缺口和下一步选择，避免最先发言的人过早影响所有人。

### 工程讨论场景

适合反复进行算法方案、产品 PRD、软件架构或设计原型评审。场景是可编辑的讨论提纲，真实执行仍由
当前 Camp 的队员、Default Lead 和 Runtime 完成。

1. 先在队员工作区配置长期角色和职责。需要标准多人 `campfire` 时，Camp 至少包含 Default Lead 和另外两位在队队员。
2. 在空 Camp 的“管理场景与小队”中，可为每个内置或自定义场景配置预设队员和负责人；自定义场景还可维护自己的角色视角、议程和交付物。
3. 创建新对话时先选择场景。预设小队会初始化本次会话的队员和负责人，你仍可在创建前临时调整；不选场景则沿用默认小队。
4. 会话创建后，场景自动填入可编辑提纲。也可在任意 Active Camp 的“队员”详情页使用“临时增加队员”，该操作只影响当前会话。
5. 补充讨论对象、已有材料、关键约束和成功标准，再添加 PRD、代码目录、架构文档、图片或原型附件。
6. 检查草稿后手动发送。只有 Default Lead 真实在队、可用 `campfire` 且在队人数满足要求时，草稿才带结构化 Skill token；其他情况会明确降级为 guided 或单人多视角提纲。

场景中的角色是本轮需覆盖的视角，不会改写队员的长期身份。自定义场景与预设小队只保存在当前设备，不同步、不进入团队记忆；
预设或临时加入后形成的 Camp 成员关系会保存在当前会话中，但不会影响其他会话。
选择场景不会自动发送、启动 Runtime、创建 Task 或修改项目文件。输入框已有正文时，需要在详情中明确选择“覆盖并填入”。

## 7. Skill 支持

Rovai 可以把启用的 Skill 兼容追加到各 Runtime 对应的项目级 Skill 目录。

在设置的 Skill 页面中可以：

- 查看内置与导入的 Skill；
- 启用或停用可管理 Skill；
- 将 Skill 分配给对应 Runtime 交付组；
- 导入本地目录或固定来源的 Skill。

Rovai 不会因为 Skill 已经投影到目录，就假定模型一定读取或正确执行了它。最终效果仍取决于 Runtime 的发现与加载能力。

## 8. MCP 支持

在设置的 MCP 页面中可以维护 External MCP，并分配给需要使用它的队员。

大多数 Runtime 会在保留原生 MCP 配置的基础上，为当前 Run 兼容追加 Rovai 分配的 MCP。Antigravity 当前只保留 Runtime 原生 MCP，不追加 Rovai External MCP。

添加 MCP 前应确认：

- 启动命令或服务地址可信；
- 凭据通过安全方式提供；
- 工具暴露范围与当前任务匹配；
- 不把密钥直接写入公开仓库。

## 9. 查看运行状态

每名正在行动的队员都有独立 Run。

在会话区和运行监控中可以查看：

- 当前状态与执行阶段；
- 工具调用和中间结果；
- 权限请求；
- 完成、失败或未完成原因；
- token 用量；
- 缓存读取、写入与命中情况；
- Runtime 和模型覆盖情况。

只有 Runtime 提供可靠结构化数据时，Rovai 才会显示对应 token 或缓存结论。没有证据的字段会保持未知。

## 10. 留下有用的团队记忆

团队记忆不等于保存全部聊天记录。

更值得留下的是：

- 为什么选择当前方案；
- 哪些分歧还没有解决；
- 哪些风险已经接受；
- 执行结果与失败原因；
- 下次不必再走的弯路；
- 哪位队员更适合处理某类问题。

在结束一段重要任务前，可以请记录型队员整理：

```text
请记录这次任务最终选择、主要理由、未解决问题、执行结果，
以及下一次继续时最先需要确认的事情。
```

这样下一次回到 Camp 时，队伍可以从已有判断继续，而不是重新解释所有背景。

## 建议的第一次任务

第一次使用时，先选择一个范围小、结果容易判断的真实任务，例如：

- 阅读一个模块并解释它的职责；
- 对一份方案进行双人追问；
- 让队伍讨论一个产品取舍；
- 修改一处小功能并查看完整 Run；
- 总结一次任务并形成团队记忆。

先观察队员之间的分工，再逐步调整角色、模型、权限和 Skill，比一开始组建过大的队伍更容易找到适合自己的协作方式。
